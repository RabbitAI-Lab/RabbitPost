协议执行链路对比

一次性请求（Request-Response）
适用于 HTTP、GraphQL (Query/Mutation)、AI 协议 — 走 POST /api/v1/execute
  • 1 浏览器 发送请求配置到 POST /api/v1/execute
  • 2 API 校验协议类型（仅允许 http/graphql/ai），鉴权，检查 Runner 可用性
  • 3 API → Runner 创建 run_job，Runner 轮询领取任务（或通过内嵌 Runner 直接派发）
  • 4 Runner 执行：变量替换 → pre-request 脚本 → 发送 HTTP 请求 → test 脚本 → 采集结果
  • 5 Runner → API 上报执行结果（run_job_result）
  • 6 API 写入 histories 表，返回 ExecuteResult 给浏览器
HTTP GraphQL AI
长连接协议（Realtime Session）
适用于 WebSocket、Socket.IO、MQTT、MCP、gRPC、SSE、GraphQL Subscription — 走 /api/v1/rt/sessions
  • 1 浏览器 POST /api/v1/rt/sessions 创建会话（protocol + url + config）
  • 2 API 选择持有 rt link 的 Runner，通过 NDJSON downlink 发送 start 指令
  • 3 Runner 建立到目标服务的协议连接（WS/MQTT/gRPC/...），事件通过 POST /runner/rt/event 回传
  • 4 API → 浏览器 事件经 SSE 推送（EventSource），含 status/message/error 帧
  • 5 浏览器 → Runner 发送消息：POST /rt/sessions/:id/send → NDJSON downlink → Runner 转发到目标
  • 6 关闭：DELETE /rt/sessions/:id → NDJSON close 指令 → Runner 断开目标连接
WebSocket Socket.IO MQTT SSE MCP gRPC GQL Subscription

Runner 选择策略（一次性请求）

1
外部在线 Runner（优先） 团队内 status=active 且 90 秒内有心跳的外部 Runner，按 lastSeenAt 降序选最新
↓ 无可用外部 Runner
2
内嵌 Runner 随 API 服务启动的 __embedded__ Runner，需已 spawn 且心跳在线（冷启动窗口内不可用）
↓ 内嵌 Runner 也不可用
3
团队内其他在线 Runner 任何 status=active 且心跳在线的 Runner（兜底）
↓ 全部不可用
F
服务端直接执行（回退） executor.ts 在 API 进程内直接执行 HTTP 请求（node:vm 跑脚本），不经过 Runner
关键设计要点：
• HTTP 请求不是直接打到 Runner 的。浏览器始终调用 POST /api/v1/execute，由 API 服务决定走 Runner 派发还是服务端直接执行。Runner 模式下 API 创建 run_job 并同步等待结果（dispatchAndWait，60s 超时轮询）。

• 长连接协议走完全不同的链路。/api/v1/execute 会明确拒绝非 http/graphql/ai 协议（返回 400 UNSUPPORTED_PROTOCOL）。长连接协议使用 rt session 模型：浏览器 ⇄ SSE+POST ⇄ API 实时桥 ⇄ NDJSON downlink ⇄ Runner ⇄ 目标服务。浏览器不直连目标，无 CORS/混合内容限制。

• 桌面模式下 local-agent 在 127.0.0.1 镜像 API 端点契约，HTTP 执行与长连接协议均可完全本机化，不经过远端服务器。

• Runner 与 API 的通信：Runner 主动轮询 GET /runner/jobs/poll 领取任务；rt 协议通过 GET /runner/rt/link 保持 NDJSON downlink 长连接接收指令，通过 POST /runner/rt/event 上行事件。

• 脚本沙箱：API 侧用 node:vm，Runner/CLI 侧用 QuickJS，统一 rp.* API（pm 为兼容别名）。
